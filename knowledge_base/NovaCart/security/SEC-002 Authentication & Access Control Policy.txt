Purpose
This document defines the official Authentication & Access Control Policy of NovaCart Technologies Pvt. Ltd. (hereinafter referred to as "NovaCart"). It establishes standardized procedures, technical authentication mechanisms, authorization frameworks, session management policies, Role-Based Access Controls (RBAC), Privileged Access Management (PAM) standards, and business rules governing identity verification and access permissions across customer accounts, internal employee portals, support microservices, and infrastructure resources.
As a core security document (SEC-002) in the Security module of the NovaCart Enterprise Knowledge Base (NEKB), SEC-002 governs technical access execution within the Identity & Access Management platform (auth.novacart.internal) and Central Directory Service, operating in strict operational alignment with COMP-001 through COMP-004, SUP-001 through SUP-005, ORD-001 through ORD-005, SHIP-001 through SHIP-007, PAY-001 through PAY-006, REF-001 through REF-006, PROD-001 through PROD-006, and SEC-001.
Scope
This policy applies universally across all authentication endpoints, user identity types (B2C Retail Customers, NovaCart Prime VIPs, B2B Merchants, Corporate Enterprise Users, Internal Employees, Third-Party Contractors, and System Service Accounts), API gateways (api.novacart.internal), and internal enterprise platforms operated by NovaCart across India, Singapore, and the United Arab Emirates.
Coverage Includes
* Authentication protocols for customer-facing interfaces, employee portals, and system-to-system APIs.
* Multi-Factor Authentication (MFA) enrollment, step-up verification, and enforcement rules.
* Cryptographic session token (JSON Web Token - JWT) issuance, renewal, inactivity timeouts, and revocation.
* Authorization mechanics governed by Role-Based Access Control (RBAC) and Attribute-Based Access Control (ABAC).
* Access request workflows, role changes, offboarding access revocations, and periodic access certification.
* Privileged Access Management (PAM), Just-In-Time (JIT) access elevation, and secure API credential management.
* Device trust scoring, geographic velocity controls, security logging, and SIEM audit retention.
Out of Scope
* Specific customer-facing account protection, recovery workflows, and password complexity criteria (governed by SEC-001).
* Cardholder Data Environment (CDE) tokenization and payment gateway secrets management (governed by PAY-006).
Authentication & Access Control Overview
Authentication and access control form the foundational security perimeter of NovaCart's digital architecture. Authentication verifies "who an entity is," while Authorization enforces "what an authenticated entity is permitted to do."
Core Security Principles
1. Zero Trust Architecture (ZTA): No user, device, network interface, or microservice is inherently trusted. Every access request—whether originating externally or from within internal corporate subnets—must be explicitly authenticated, authorized, and cryptographically verified prior to granting resource access.
2. Principle of Least Privilege (PoLP): Users, software agents, and service microservices are granted the absolute minimum level of access permissions necessary to perform their assigned job functions or operational duties.
3. Segregation of Duties (SoD): High-risk administrative and financial actions (e.g., code deployment to production, manual refund disbursements exceeding threshold limits, database schema modifications) require dual-person authorization controls to prevent single-agent fraud or operational failure.
4. Defense in Depth: Enforcing multi-layered security barriers comprising strong authentication, contextual risk scoring, network segmentation, role-based authorization, continuous session monitoring, and real-time anomaly detection.
Authentication Principles
All identity validation processing within NovaCart must adhere to three non-negotiable architectural mandates:
* Centralized Identity Provider (IdP): All customer and enterprise employee authentication requests must route through auth.novacart.internal. Disconnected or localized password databases across individual microservices are strictly prohibited.
* Cryptographic Credential Transport: Authentication transactions must execute exclusively over TLS 1.3 encrypted channels using secure cipher suites. Plain-text credential transmission is blocked at the edge API gateway.
* Mutual API Authentication (mTLS): System-to-system microservice communications must utilize Mutual TLS (mTLS) with short-lived X.509 digital certificates issued by NovaCart’s internal Certificate Authority (CA).

	MFA Enforcement Rules
* Mandatory Employee MFA: $100\%$ of internal employee, contractor, and administrative logins require MFA completion via FIDO2 keys or TOTP apps upon every SSO session initiation.
* Adaptive Step-Up Customer MFA: B2C customers are prompted for MFA when logging in from an unrecognized device, initiating high-value transactions, modifying contact details, or viewing stored payment card tokens (SEC-001, PAY-006).

	Session Termination & Revocation Protocols
1. Explicit Logout: Triggering logout invalidates the client-side session token and broadcasts a revocation signal to the Redis Token Blacklist Cluster.
2. Password / Credential Change: Modifying a user password, primary email, or MFA setting instantly revokes all active session tokens across all registered devices (LOGOUT_ALL_DEVICES) (SEC-001).
3. Admin Revocation: Security Operations Agents can execute instant session termination for any compromised customer or employee account via shield.novacart.internal.

	Access Revocation & Employee Offboarding
* Immediate Revocation: Upon employee termination or contractor contract completion, HR dispatches an automated offboarding webhook to auth.novacart.internal. All active SSO sessions, VPN tokens, and RBAC roles are revoked within $< 5 \text{ minutes}$.
* Role Change Recalculation: When an employee transfers to a new department, old RBAC permissions are revoked automatically before new role entitlements are provisioned ("Zero Residual Rights").

	Device & Location-Based Access Controls
Location telemetry and device trust scoring evaluated dynamically by auth.novacart.internal influence access decisions:
* Device Trust Scoring: Internal enterprise portals assess client health (active corporate EDR agent, disk encryption status, OS patch level). Non-compliant or personal unmanaged devices are blocked from accessing production environments.
* Geographic Velocity Verification: Access attempts exhibiting impossible travel velocity (e.g., login from Bangalore followed by a login from London 30 minutes later) trigger immediate session termination, account lock, and Security Operations notification (SEC-001).
* Anonymizer & Proxy Blocking: Access requests originating from known TOR exit nodes, commercial VPN proxies, or malicious IP subnets identified by threat intelligence feeds are auto-rejected at the edge API gateway.
Customer Responsibilities
Customers accessing NovaCart digital services must uphold basic security hygiene:
1. Protect Authentication Credentials: Keep passwords, PINs, and authentication tokens confidential. Never share OTPs or session magic links with third parties.
2. Maintain Authenticator Security: Ensure mobile devices used for TOTP or SMS OTP reception are secured with screen lock PINs or biometrics.
3. Secure Log Out on Shared Devices: Always execute explicit logout when accessing NovaCart accounts from public or shared computer terminals.
Employee Responsibilities
Internal NovaCart employees, contractors, and third-party staff must adhere to strict access rules:
1. Zero Credential Sharing: Sharing corporate credentials, SSO passwords, VPN tokens, or physical FIDO2 security keys is strictly prohibited and constitutes grounds for immediate termination.
2. Lock Unattended Workstations: Lock physical computer screens (Win + L / Cmd + Ctrl + Q) whenever leaving workstations unattended.
3. Prompt Access Discrepancy Reporting: Report unexpected access entitlements or suspicious access requests to the IT Security Helpdesk immediately.

	Business Rules
Rule 1: Mandatory Centralized Authentication Rule
No software engineering team or third-party vendor may build, deploy, or maintain an independent user authentication table or password store. All user authentication must delegate strictly to auth.novacart.internal.
Rule 2: Segregation of Production and Non-Production Access
Development and testing environments must be completely isolated from Production environments. Developer accounts permitted in Staging environments are strictly blocked from accessing Production databases containing live customer PII or payment records.
Rule 3: Comprehensive Authentication Audit Logging Standard
All authentication attempts (successes and failures), MFA challenges, session creations, access elevation events, and authorization rejections must be logged continuously to SIEM storage with source IP, device fingerprint, timestamp, and User ID, retained for a minimum of 7 years.
Exception Handling
* Emergency Just-In-Time (JIT) Break-Glass Protocol: In the event of a catastrophic production outage where standard ticketing systems are unreachable, an engineer may trigger a "Break-Glass" emergency override. This action dispatches real-time alerts to the CISO, logs video recordings of all commands, and automatically expires after 1 hour.
* Lost Employee MFA Token Procedure: An employee who loses their physical FIDO2 security key must complete in-person or video identity verification with IT Security before a temporary 8-hour bypass code is generated.
Practical Examples
Scenario 1: Customer Step-Up Authentication during Password Change
1. B2C Customer attempts to change their account password inside My Account.
2. System evaluates session context: Customer is on a recognized home Wi-Fi network, but password modification is classified as a Level 3 High Security action (SEC-001).
3. auth.novacart.internal requires step-up MFA verification, dispatching a 6-digit OTP to the customer's verified mobile number.
4. Customer enters the OTP successfully. Password updates, and all other active sessions across mobile apps and web browsers are immediately invalidated (LOGOUT_ALL_DEVICES).
Scenario 2: Support Representative Role-Based Access Control (RBAC) Enforcement
1. Customer Support Agent (assigned ROLE_SUPPORT_L1) attempts to view a customer's payment details in crm.novacart.internal.
2. API Edge Gateway checks the agent's JWT token scope against the authorization policy.
3. The gateway permits viewing masked transaction logs but blocks access to raw credit card numbers or unmasked token vault data, returning 403 Forbidden for unmasked endpoints (PAY-006).
Frequently Asked Questions (FAQs)
Q1: What is the difference between SEC-001 (Account Security) and SEC-002 (Authentication & Access Control)?
Answer: SEC-001 focuses on customer-facing account protection, password complexity, identity recovery workflows, and account takeover containment. SEC-002 defines the technical identity infrastructure, authentication protocols (OAuth/SAML/mTLS), Multi-Factor Authentication (MFA) enforcement, session token architectures, Role-Based Access Control (RBAC), and internal Privileged Access Management (PAM).
Q2: Why does my admin session log me out automatically after 15 minutes of inactivity?
Answer: In accordance with our enterprise session management standards, administrative and employee portals enforce a strict 15-minute inactivity timeout to prevent unauthorized access in the event an administrative workstation is left unattended (SEC-001).
Q3: How is privileged access granted to systems engineers during production emergencies?
Answer: Production access is not granted permanently. Engineers must request Just-In-Time (JIT) access elevation through our PAM portal, linking a valid incident ticket. Upon approval by a DevOps Lead or CISO, temporary access is granted for a maximum window of 1 to 4 hours, during which all session activities are recorded for security auditing.
